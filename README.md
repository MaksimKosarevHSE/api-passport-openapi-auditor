# API Passport — локальный аудитор OpenAPI-контрактов

Учебный мини-проект команды KIB-28 для Блока 2 домашней работы по кибербезопасности.

## 1. Проблема, пользователь и проверяемый результат

Для разработчика небольшой компании, выпускающей веб-сервис с API, существует проблема: в OpenAPI-контракте могут остаться операции без явно заявленной аутентификации, слабые способы передачи ключей и неописанные ответы авторизации. Это увеличивает риск ошибок контроля доступа и затрудняет проверку перед релизом.

Команда проверяет, может ли локальный статический анализатор за время до одной минуты:

- разобрать синтетический OpenAPI 3.0/3.1 JSON;
- найти все заранее внесённые критичные пробелы в 12 тестовых сценариях;
- дать разработчику понятный приоритетный план исправлений;
- не отправлять контракт или тестовые данные по сети.

Метрика MVP: 12/12 автоматических тестов движка и полный демонстрационный сценарий от загрузки контракта до выгрузки отчёта.

## 2. Решение

API Passport — одностраничное веб-приложение без сервера и внешних зависимостей. Пользователь загружает или вставляет OpenAPI JSON, после чего браузер локально:

1. перечисляет HTTP-операции;
2. вычисляет эффективное поле `security` с учётом глобального значения;
3. проверяет ссылки на `components.securitySchemes`;
4. отмечает HTTP без TLS, API-ключ в query и Basic Auth;
5. ищет чувствительные поля в request/response schema;
6. проверяет ответы 2xx, 401 и 403;
7. формирует индикативную оценку и приоритетный план.

Приложение не подключается к указанным в контракте серверам и не выполняет сканирование.

## 3. Актуальность по коллективной базе знаний

- `SRC-067`, Indusface, *State of Application Security 2026*: по записи банка число атак на один API-хост в сегменте МСБ выросло на 404% к 2024 году, а атаки с эксплуатацией API-уязвимостей — на 181% (с. 6 и 8 отчёта). Источник относится к телеметрии AppTrana и не описывает весь рынок, поэтому используется как индикатор, а не универсальная статистика.
- `SRC-070`, Kroll, *State of Application Security: Our View from the Front Lines of Technical Assessments*: по записи банка нарушения контроля доступа составили 41,2% выявленных уязвимостей высокой и критической степени, а 47% таких нарушений связываются с решениями на этапе проектирования (с. 21 и 25).
- Дополнительное подтверждение из текущего банка: Akamai, *2026 API Security Impact Study* — 87% опрошенных организаций сталкивались с API-инцидентами, а только 23% знают, какие API передают конфиденциальные данные (с. 2–3 по аннотации реестра).

## 5. Ресеч платформ запуска и выводы

Изучены Product Hunt, DevHunt и Hacker News Show HN, а также обзор LaunchList, указанный в методичке.

- Product Hunt требует ясного name/tagline/description, хотя бы одного изображения и работающей ссылки. Рекомендуется показывать продукт в действии и просить конкретную обратную связь, а не голоса.
- DevHunt подходит точнее широкой витрины, потому что API Passport — инструмент разработчика. Запуски идут недельными циклами, постоянная карточка бесплатна, а выбранная launch-неделя сейчас платная.
- Show HN принимает то, что пользователи могут реально попробовать без барьеров. Уместен открытый локальный проект с понятным техническим объяснением, но правила запрещают сгенерированный текст в постах и накрутку обсуждения.

Выводы для продукта:

1. Обещание ценности должно называть действие и пользователя: «Локально найдите пробелы защиты в OpenAPI до первого запроса», а не «новая платформа API Security».
2. Демо должно открываться без регистрации и сразу давать синтетический пример с заметным результатом.
3. Для проверки гипотезы лучше сначала провести закрытый учебный тест, затем при наличии разрешения показать проект разработчикам на DevHunt или Show HN; публичный запуск для выполнения задания не требуется.

## 6. Установка и воспроизведение демо

Зависимости и установка не нужны.

Вариант 1: откройте `index.html` двойным щелчком.

Вариант 2: в папке проекта запустите локальный сервер:

```bash
python3 -m http.server 4173
```

Затем откройте `http://127.0.0.1:4173/`.

Демо:

1. Нажмите «Рискованный магазин».
2. Нажмите «Выполнить локальный аудит».
3. Покажите высокий риск, HTTP без TLS, открытую операцию оплаты и query API key.
4. Отфильтруйте только высокие находки.
5. Скачайте JSON-отчёт.
6. Загрузите «Готов к релизу» и покажите отсутствие высоких находок.

## 7. Тестирование

Откройте `tests.html`. Заголовок вкладки должен стать `PASS · API Passport tests`, а итог — `12/12 тестов пройдено`.

Ручные security-проверки:

- не выполняются `fetch`, XHR, WebSocket и обращения к URL из спецификации;
- пользовательские значения выводятся через `textContent`, а не как HTML;
- файл ограничен 1 МБ;
- неподдерживаемый OpenAPI 2.0 отклоняется понятной ошибкой;
- неизвестная схема аутентификации даёт отдельную высокую находку;
- пустой `paths` не приводит к падению.

## 8. Модель угроз MVP

Активы: OpenAPI-контракт, локальный отчёт, доверие пользователя к результату.

Основные угрозы и меры:

- утечка контракта — нет сервера и сетевых запросов;
- XSS через название/путь — динамические строки вставляются через `textContent`;
- зависание на чрезмерном файле — лимит 1 МБ и ограниченная глубина обхода схемы;
- ложное чувство защищённости — интерфейс и отчёт явно называют оценку индикативной;
- использование для атаки чужой системы — приложение не отправляет запросы и не сканирует адреса.

## 9. Ограничения и план развития

Ограничения:

- только OpenAPI 3.0/3.1 JSON, YAML не поддерживается;
- `$ref` не разворачивается между файлами;
- эвристика чувствительных полей зависит от названий;
- не проверяются runtime-авторизация, бизнес-логика, rate limiting и фактический TLS;
- оценка не является сертификатом безопасности.

Следующие шаги: безопасный YAML-парсер, локальное разрешение `$ref`, настраиваемые правила, экспорт HTML/PDF, интеграция в CI и проверка результатов на размеченном наборе синтетических контрактов.
